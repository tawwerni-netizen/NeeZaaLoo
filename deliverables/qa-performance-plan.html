Matchmaking & gameplay

Vs Computer

verified live
Played a full chess game this session — move submission, AI reply, and clock all confirmed working over the real WebSocket gateway.
  • Close the tab mid-game, reopen, log back in — does ActiveMatchBanner find the live duel and let you resume, or is it silently orphaned?
  • Kill wifi for 15s mid-move, restore — does the clock keep running server-side (it should — server is the clock authority) and does the client resync without desyncing the board?
  • Let the clock hit zero while disconnected — confirm the duel settles on reconnect, not stuck "live" forever.
  • Rapid double-click the same square/piece — confirm no duplicate move submission (intent should be idempotent per turn).

Random opponent (matchmaking queue)

backend proven
Queue has a real TTL + heartbeat sweep and a partial unique index preventing double-queueing (already unit tested). The realtime gateway has a lease manager (LEASE_MS=15000) and a claim-sweep tick every 3s that reclaims a duel if its owning gateway instance dies.
  • Queue, then immediately queue again from a second tab — confirm ALREADY_QUEUED (409), not a second ticket.
  • Queue and close the tab before a match is found — wait past the TTL, confirm the stale ticket is swept and doesn't permanently occupy the matchmaking pool.
  • One player disconnects the instant a match is found (before either client renders the board) — does the other player get seated correctly, and does the disconnector's reconnect resume into the same duel?
  • Cash-tier specifically: queue for a CASH ticket with exactly the stake amount as your balance, then a second CASH ticket immediately after — confirm the second is rejected, not a double-lock on the same funds.

Direct friend challenges

backend proven
A challengeExpiryWorker tick already exists; "accept an already-resolved challenge" is unit tested (returns NOT_PENDING, not a duplicate duel).
  • Both players click "accept" within the same second — confirm exactly one duel is created, not two.
  • Challenger cancels the instant the opponent clicks accept — which one wins the race, and is the loser told clearly why (not a silent failure)?
  • Let a challenge sit until it expires while the recipient has the popup open — does the UI update live, or does clicking a dead challenge produce a confusing error?

Tournaments

backend proven
8-phase lifecycle (DRAFT→...→SETTLED) with its own sweep worker bridging ordinary duel results into the bracket and auto-advancing rounds.
  • Disconnect mid-match during a LIVE tournament round — confirm the bracket doesn't stall waiting on a match that will never report back (check the sweep's timeout handling specifically).
  • Register right as REGISTRATION closes — is the boundary handled cleanly (either in or a clear rejection), or is there a race where you're charged the entry fee but not seated?
  • Confirm a withdrawn/disconnected player's opponent in the next round gets a bye or walkover, not an infinite wait.

PART 2

Performance & hosting optimization

The platform runs as one Node process (server.js) fanning out to four children — Next.js, the API, the realtime gateway, and the worker — all on one Hostinger host. That shape drives most of what matters below.

Already fixed: earlier in this project's life, a single open browser tab generated 46,000+ requests in ~20 minutes — roughly 10 uncoordinated setInterval polling loops, several firing every second, stacked with no cleanup. Verified live tonight: that's down to ~4 requests/second on the dashboard. Whoever fixed it did it right — keep watching for regressions (see checklist below), this class of bug is easy to reintroduce one new component at a time.

Frontend (Next.js)

  • Polling audit, recurring: before every merge that touches a page with live data, grep for new setInterval calls under 5 seconds. One new component polling every 1s is how the 46k-request bug happened the first time.
  • Run next build and check the bundle analyzer output — flag any single game board component (Chess/Backgammon/etc.) pulling in more than its own game's code via a bad shared import.
  • Confirm game board SVG/asset packs are only fetched for the game actually being played, not all 10 up front on the /play hub.
  • In DuelShell and the board components, verify a WebSocket state update triggers a re-render of only the changed squares/pieces, not the whole board tree — React DevTools Profiler during an active game is the fastest way to see this.
  • Confirm images use Next's <Image> (already true for the hero/game-card WebP assets per this session's network trace) everywhere, not raw <img>, for automatic lazy-loading below the fold.
  • Check font loading — _next/static/media/*.woff2 requests were firing on every navigation in tonight's trace; confirm font-display: swap and that they're cached long-term (immutable), not re-fetched per page.

Backend & database

  • Add EXPLAIN ANALYZE to the homepage/leaderboard queries (/v1/tournaments, /v1/duels/live, global-skill lookups) — these are hit by every logged-in user on every page load.
  • Cache the public leaderboard and homepage tournament list — they don't need per-request freshness. A 5–15s in-memory or Redis cache on these specific reads cuts real DB load without touching anything money-related (never cache wallet balances, duel state, or anything the ledger owns).
  • Check pg_stat_statements (or Supabase's query insights) for the slowest queries after a day of real traffic — optimize by evidence, not guesswork.
  • WebSocket connection limits: the gateway has per-connection rate limits already (RATE_LIMIT_CAPACITY, chat's own separate budget) — confirm ulimit -n / Hostinger's process file-descriptor limit is high enough for your expected concurrent-connection count, since a single Node process holds every open socket.
  • Watch memory on the 4 child processes under load (server.js spawns Next.js, API, Gateway, Worker) — if one leaks or spikes, it can crash-loop and take the reverse proxy's readiness probe down with it (this exact failure mode is referenced in this session's own commit history: "resolve api 502 bad gateway crash loop").
  • Since deposits/withdrawals now run through independent chain reads (chain.verifyIncoming / verifyTransfer), confirm the TRON RPC endpoint you're using has headroom — every pending deposit and every in-flight withdrawal polls it on the reconciliation worker's tick.

Mobile UX

  • Test every board (Chess, Backgammon, Dominoes, etc.) at 375px width specifically — pieces need a minimum comfortable touch target; verify none require pixel-precision taps.
  • Kill mobile data mid-move (airplane mode for 5s, restore) — same reconnect test as desktop, but confirm the mobile UI shows a visible "reconnecting" state rather than looking frozen.
  • Test the deposit QR modal on an actual phone — can the camera scan it cleanly at the modal's rendered size?
  • Confirm the bottom nav / active-match banner don't overlap the on-screen keyboard when typing in chat.
