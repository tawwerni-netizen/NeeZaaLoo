01 — VISION

What this is, and what it is not

A global skill duel platform: one account, one rating ecosystem, one wallet, one matchmaking core, one tournament engine, one trust & safety layer — with many short-form 1v1 games behind it. Chess is the flagship game. Chess is not the category.

It is not a chess website, and it is not a betting product. Those two sentences constrain every decision downstream: the name, the homepage, the information architecture, the colour palette, and the copy.

The emotional message is never "deposit money and gamble." It is: "I want to test my skill" → "I can compete" → "I can improve" → "I can climb" → and, only where legally permitted, "I can compete for prizes."

The product in one architectural sentence

A Skill Duel Engine with pluggable games sits on top of a shared platform (identity, matchmaking, rating, wallet, ledger, tournaments, risk, fair play, compliance), so that adding a new game never requires rebuilding financial infrastructure. If a future engineer has to touch the ledger to ship a new game, the architecture has failed.

Game roadmap and the veto rule

PhaseGames
1 — FlagshipChess
2Speed Math · Memory Grid · Pattern · Number Memory · Reaction · Precision
3 — Evaluated / free-play onlyConnect Four · Checkers · Reversi · Backgammon · Seega · Gomoku · Dominoes · XO

No game ships because it is popular. Every candidate is scored on a twelve-criterion scorecard; a low score on cheating risk or server authority is an absolute veto no total can override. That veto already excludes Connect Four, Checkers, and Reversi from cash play — Connect Four is strongly solved, so a cash game on it transfers money from honest players to whoever downloads the solver first.

Business model

Configurable rake: standard 10–15%, VIP 8–10%, tournaments custom — driven entirely by the Economy Rules Engine, never hardcoded. No profit is promised or projected as guaranteed; the economics only work if the platform is trusted, which is why anti-cheat, the ledger, and compliance are core product, not overhead.

The four things that would end this company

1A broken ledger — if we cannot say what we owe, nothing else matters.
2Loss of custody — a drained hot wallet.
3Loss of competitive integrity — the day cheating becomes common knowledge.
4Operating where not permitted — a legal, not an engineering, failure.
02 — FOUNDING RULES

The rules that govern every decision here

  1. The client renders; the server decides. Nothing client-asserted is trusted for money, results, scores, state, clocks, or ratings.
  2. A mutable balance is never the source of truth. Double-entry, append-only; balances are derived from entries.
  3. A webhook is a notification to go look, never a reason to credit.
  4. Never one signal = ban. Signals → score → evidence → case → review → decision → appeal.
  5. No unexplained discrepancy is ever auto-repaired.
  6. Adding a game must never require touching financial infrastructure.
  7. No secret in any client. No private key in any repository or APK.
  8. Compliance is configuration, not conditionals. Every market defaults to free-play-only until counsel says otherwise.
  9. The money surfaces feel like a bank. The game surfaces feel like a sport. Nothing ever feels like a casino floor.

Why realtime is a separate deployable: game sockets are bursty, long-lived, and stateful. The money path is low-throughput and must never be starved by a chess rush hour, and a socket gateway crash must never take REST or settlement with it.

Why admin is a separate deployable: admin holds the most dangerous capabilities in the system. It gets its own deployable, its own auth realm, its own network exposure, and its own audit stream — an RCE in the public API must not be an RCE in the admin plane.

Server authority — the non-negotiable list

ConcernAuthorityEnforcement
Money, balancePostgres ledgerDerived from entries, never stored as truth
Game resultDuel engine (server)Client sends intents; server produces events
Score, state, clockServer / game pluginClient holds a projection it may not author
RatingRating serviceComputed post-settlement from server's own result
Payment / withdrawalPayment service + ledgerOnly from verified provider/chain state; never client-advanced

Every client→server game message is an intent (SubmitMove, Resign); every server→client message is an event (MoveAccepted, DuelSettled). There is no message shape in which a client asserts a result — enforced at the protocol schema level.

04 — SKILL DUEL ENGINE

The Skill Duel Engine & plugin contract

SkillDuelEngine  (owns: lifecycle, clock, persistence, events, settlement)
├── ChessPlugin        ├── DominoesPlugin
├── SpeedMathPlugin    ├── BackgammonPlugin
├── CheckersPlugin     ├── SeegaPlugin
├── ConnectFourPlugin  ├── ReversiPlugin
├── XOPlugin           └── GomokuPlugin

The engine owns everything touching money, identity, or trust. A plugin owns only the rules of its game. Four properties the contract buys: purity (pure functions, fully unit-testable, exact replay verification), server-generated challenges (the seed is never sent to the client before content is due), projection (project() guarantees a client never receives data it should not have — if it's not in the projection, it's not on the wire), and signals not verdicts (a plugin can report an anomaly; it cannot ban anyone — enforced by the type system).

Duel lifecycle

CREATED → RESERVED → READY → LIVE → COMPLETED → SETTLED
                                              ↘ ABORTED / VOIDED

RESERVED: entry fees move to a locked ledger position before the duel starts — no duel with money attached ever begins with unlocked funds. COMPLETED vs SETTLED are deliberately distinct steps, so a settlement failure can be retried without re-running the game, and a duel under fair-play hold can sit in COMPLETED indefinitely.

Game selection scorecard

Weighted 12-criterion score; a game needs ≥70% of maximum and ≥4/5 on both cheating-risk and server-authority to enter development — a high total cannot compensate for a low cheat-risk score.

GameCheat riskServer authorityVerdict
Chess2/55/5Ship. Flagship; heaviest anti-cheat investment.
Speed Math / Memory / Pattern4/55/5Ship.
Reaction / Precision3/54/5Ship with caution. Latency-oracle risk — consider free-play only.
Connect Four / Checkers / Reversi1/5 — solved/near-solved5/5Never cash. Free-play only.

06 — MONEY

The ledger

Every transaction sums to zero, per asset. Therefore the system always balances, or it refuses the write. Balances are derived by summing entries; a mutable balance column is never the source of truth.

Account model

Wallet states are distinct accounts, not a status flag on one balance — "locked" funds live in a different account, so a query for available balance cannot accidentally include them.

AccountMeaning
user:{id}:availableSpendable now
user:{id}:lockedCommitted to a live duel or pending withdrawal
user:{id}:pendingDeposit seen, not yet finalised
user:{id}:withdrawableCleared, eligible for withdrawal
platform:suspenseThe honesty account. Unexplained funds land here and raise a case — never auto-cleared.

Enforced invariants (all at the database layer)

I1Every transaction sums to zero per assetDeferred constraint trigger
I2Entries are immutableRevoked UPDATE/DELETE + trigger
I3No user account goes negativeChecked under row lock
I4Idempotency keys are uniqueUnique index — a retry cannot double-post
I5Adjustments require a reason + admin actorCHECK constraint

Reconciliation runs continuously at three levels — L1 internal (snapshot vs. entries), L2 provider (our records vs. NOWPayments), L3 chain (custody vs. actual on-chain balance) — plus a global solvency check: SUM(custody) ≥ SUM(liabilities) per asset. A failure triggers an immediate automated withdrawal halt and pages a human. Discrepancies always produce ALERT → CASE → REVIEW, never a silent repair.

07 — PAYMENTS

Payments

MVP asset: USDT · MVP network: TRON (TRC20), one network only · Provider: NOWPayments, behind a PaymentProvider abstraction the core platform never sees past.

A webhook is a notification to go look. It is never the reason we credit. Credit happens only after independent on-chain verification of asset, network, amount, destination, and confirmation depth.

Withdrawal state machine

REQUESTED → VALIDATING → RISK_CHECK → PENDING_REVIEW → APPROVED
         → PROCESSING → BROADCASTED → CONFIRMED → COMPLETED
                      (or FAILED | REJECTED | CANCELLED)

Funds lock at REQUESTED. No transition is ever triggered by a client call. Four-eyes approval above a configured threshold — no single admin can both initiate and approve. Nine gates must all pass: balance, KYC, geo, age, address allowlist, security cooling-off, risk score, fair-play hold, and global solvency.

Custody

Unresolved, blocks Phase 5 (founder + counsel decision). Options on the table: full provider custody, qualified third-party custodian, or MPC/HSM self-custody. Whatever is chosen: no private key in source code or the APK, ever; hot-wallet float capped and topped up from cold storage on a schedule; signing is a separate, minimal-surface service.

08 — TRUST

Anti-cheat & fair play

Governing rule: never one signal = ban. Signals → Risk Score → Evidence → Case → Review → Decision → Appeal. The plugin contract enforces this structurally — fairPlaySignals() returns signals and has no type-level way to express a verdict.

Chess-specific detection (the hardest problem in the product)

Free engines exceed every human, so detection is statistical, never certain: engine correlation, ACPL, critical-position accuracy (the most discriminating signal — humans degrade on only-move positions, engines don't), move-time distribution, rating-performance delta, longitudinal consistency, and selective assistance. Thresholds come from labelled data, not intuition — this dataset does not exist yet (open item A1), so chess detection currently produces cases for human review with no automated sanctions.

Anti-collusion

Modelled as a graph problem: nodes are accounts/devices/IPs/payment instruments; edges are shared device, shared funding, repeated pairing, value flow. Abnormal pairing frequency is computable exactly, since the platform controls matchmaking and knows the expected meeting distribution.

What may be automated vs. what always needs a human

ClassAuto-action?
Physically impossible input; confirmed multi-account self-playYES
Statistical engine correlation; collusion graph anomaly; input-biometric anomalyNO — always human
09 — TRUST

Compliance & trust

A separate policy layer every sensitive action consults — never conditionals scattered through feature code — able to change a market's status by configuration, not deployment. Fail closed: if the policy engine cannot reach a dependency, real-money actions are denied; free play continues.

Default posture

Every country starts UNDETERMINED → ALLOW_FREE_PLAY_ONLY — no real money by default. A market becomes real-money eligible only by an explicit, counsel-backed, audited change.

KYC tiers

TierTriggerUnlocks
0RegistrationFree play, ranked play
1First depositCash duels within limits
2Withdrawal / volume thresholdWithdrawals within limits
3High volume / risk flagElevated limits

KYC is enforced at the withdrawal boundary at minimum — a platform that allows anonymous deposit→play→withdraw is a laundering vehicle. Documents live in separate encrypted storage with their own retention clock.

10 — SECURITY

Threat model

STRIDE per trust boundary, re-run at every phase gate. Three of the top four assets at risk are not classic security problems — a perfectly hardened server with a working cheat is a dead company.

#AssetSeverity
1Ledger integrityTerminal
2Custody / withdrawal controlTerminal
3Competitive integrityTerminal
4Regulatory standingTerminal

Highest-value attack surface: payment provider webhooks. A forged webhook that credits a balance is a direct mint. Mitigation: HMAC verification before parsing (constant-time), idempotency on provider event id, and mandatory independent on-chain confirmation before any credit — never the webhook alone.

Everything left of the client is hostile — the Android APK will be decompiled and the WebSocket protocol reverse-engineered. There is no client-side secret and no client-side check that matters.

Standing security requirements

No secret in any client · no private keys in application code or servers · deny by default on every endpoint (unannotated endpoints fail closed in CI) · all financial mutations idempotent and audited · fail closed on money, fail open on fun.

Frontend ↔ API wiring

The root cause of the original "signup does nothing" production bug: apps/web/src/lib/api.ts defaults NEXT_PUBLIC_API_URL to http://localhost:3000 when the variable isn't set at build time (Next.js bakes NEXT_PUBLIC_* vars into the JS bundle — setting them after the build has no effect). Similarly apps/web/src/lib/use-duel-socket.ts defaults NEXT_PUBLIC_GATEWAY_URL to ws://localhost:3010.

Required on nizalo.com's environment variables, before the next build:

NEXT_PUBLIC_API_URLhttps://api.nizalo.com
NEXT_PUBLIC_GATEWAY_URLwss://[gateway host — apps/gateway not yet deployed as of this doc]

apps/gateway (the realtime WebSocket server for live duels/chat) has not been deployed to production yet. Only apps/web and apps/api are live. Realtime play, live duel spectating, and chat will not function until apps/gateway is deployed to a domain/port reachable over wss:// and NEXT_PUBLIC_GATEWAY_URL is wired to it — this is the next infrastructure gap after this document was written.

Known open items from this deployment pass

  • Confirm DATABASE_URL on api.nizalo.com is the real Postgres URI (not a Supabase REST URL) and that migrations have been run against it.
  • Set NEXT_PUBLIC_API_URL=https://api.nizalo.com on nizalo.com and trigger a rebuild (this variable only takes effect at build time).
  • Deploy apps/gateway for realtime features; wire NEXT_PUBLIC_GATEWAY_URL.
  • Deploy apps/worker (settlement, reconciliation, tournament sweeps) — not covered in this pass; without it, cash settlement and tournament automation will not run in production.
  • A double-modal rendering bug was observed on the signup form (cosmetic, non-blocking).
  • Any Supabase key pasted into a chat/session during this setup should be rotated as a precaution (Project Settings → API).
13 — LOCAL DEV

Running and testing locally

npm install
npm test              # 2,122+ tests across 37 workspaces, PGlite (Postgres 17 in WASM)
npm run typecheck
npm run build --workspace=apps/web
npm run start --workspace=apps/web

Tests run against PGlite — real PostgreSQL 17 compiled to WASM, in-process, no Docker required. This proves every constraint, trigger, and plpgsql function exactly as production, with one limitation: PGlite is single-connection, so genuine concurrency (row-lock contention, deadlocks, serialisation failures) is not exercised by the default suite. Real-Postgres concurrency scenarios live in */real-pg-concurrency.test.mjs files and use packages/ledger/test-support/real-pg-db.mjs to provision a disposable database per test file against TEST_DATABASE_URL (defaults to postgres://postgres:postgres@localhost:5432/skill_platform_test) — a real local or containerised Postgres is required to run these.

A PGlite-socket bridge is available for standing up a full live dev environment (API + web dev server) with no local Postgres install at all — see the project memory note "Smoke-test env via PGlite-socket" for the exact recipe.
